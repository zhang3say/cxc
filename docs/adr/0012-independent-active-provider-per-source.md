# 0012-independent-active-provider-per-source

## Status
accepted

## Context & Decision
在处理 Codex 和 Claude 的多运行环境（Source：如 Desktop App 和 WSL）时，我们面临如何管理启用节点（Active Provider）状态的问题。早期的设计中，`Active Provider` 是跟随 `Target Tool`（目标工具）全局唯一的（例如 `codex_active`），这导致如果用户从 App 切换到 WSL，当前选中的节点会被自动带入并应用到新环境中。

经过讨论，为了符合用户对“不同执行环境应当独立”的心智模型，我们决定：

1. **状态独立化**：同一个 `Target Tool` 下的不同执行环境（Source，如 App 和 WSL）将拥有独立的激活状态记录。这意味着在 App 中启用的节点和在 WSL 中启用的节点互不干扰，互相独立记忆。切换到 WSL 时，应该显示 WSL 上次启用的节点（如果是第一次切，则显示没有启用任何节点）。
2. **列表共享化**：尽管激活状态独立，但中转节点（Provider）配置列表本身依然全局共享。用户在一个环境中添加的节点，可以在另一个环境中无缝看到并选择启用。

这一设计在配置结构上要求将 `codex_active` 拆分或扩充为针对特定 Source 的独立字段，确保用户在切换环境时，看到的不仅是正确的路径，还有该环境下真实启用的独立节点。

## Considered Options
* **完全共享状态**（旧方案 / 被否决）：切换 Source 仅仅改变了写入路径，但 UI 继续显示同一个 Active Provider，并直接写入新路径。这会让认为环境是独立的用户感到困惑。
* **完全独立节点列表**（被否决）：在 App 和 WSL 维护两套完全隔离的 Provider 列表。虽然状态彻底解耦，但会造成极其繁琐的配置冗余，用户如果想在两个环境用同一个 Endpoint 需要配置两遍。
* **共享列表 + 独立状态**（选用）：在保障了用户免于重复配置的同时，允许各运行环境维持各自的激活现场，完美平衡了便利性与逻辑严谨性。
